# 佣金与奖金分成设计

> 业务口径以 [业务真相.md](业务真相.md) 为准，技术约束以 [ARCHITECTURE.md](ARCHITECTURE.md) 为准。
> 本文只回答一件事：**把"达成率定倍数 + 关系分账 + 预算池按成单顺序"落进现有六段纯函数内核**，需要动哪些模型、加哪几段、守哪些不变式。

---

## 0. 结论先行

三个判断决定全部设计，其余都是推论：

| 判断 | 后果 |
|---|---|
| **达成率是期间级函数，不是订单属性** | 流水线必须两趟：先归集全期业绩算系数，再逐单算钱。不能边算边查 |
| **业绩归属 ≠ 佣金归属** | 需要两张独立的图：一张决定谁冲指标，一张决定钱给谁。混用会让 AS 分账后达成率自己掉下来 |
| **奖金池是预算，不是费率** | 池总额来自事实（预算），发放条件来自规则（FIFO 消耗 + 分发方式）。规则改版不得改预算 |
| **档位是倍数，基准费率单独配（Q1 已定）** | `amount = base × BaseBPS × 档位倍数 × 时间 × 产品 × 区域`，全链一次舍入 |

一句话概括目标形态：

```
目标额 + 成单(合同/收入) ──► 达成率 ──► 档位倍数 ──┐
基准费率(产品线×角色) ───────────────────────────┤
                                                  ├─► 单笔佣金 ──► 分账(SS/AS) ──► 池领取/分发 ──► 管理链 ──► 结算
成单季度 × 产品 × 区域 ─────────► 因子倍数 ───────┘
```

已定口径速查（详见各节）：双口径同时算（§5.1）· 池按收入口径领取（§5.2）· 目标额不按月折算（§11）· 区域是乘数不进 `PhaseDirect`（§4.3.1）· 管理奖基数为分账前全额、池不上溯（§7.1 / §8.4）。

## 2. 三个决定性建模判断

### 2.1 达成率必须两趟算

达成率 = 期间累计实际 ÷ 期间目标。它依赖"这个人在本期一共成了多少单"，而单笔佣金又依赖达成率。这是唯一的前后依赖，必须显式拆成两趟：

```
第 1 趟（阶段 0）：扫全部订单行，按业绩归属累加 Actual，除以 Target，定档
第 2 趟（阶段 1~8）：拿定好的档位逐单算钱
```

**不做**的事：边算边累积、把已算比例回头修正。那会让结果依赖订单遍历顺序，且无法回答"为什么第 3 单的比例和第 10 单不同"。

依赖图无环：业绩归属只取决于「谁是成单人 / 规则怎么分业绩」，与系数无关；系数只取决于达成率，与金额无关。所以两趟是充分且必要的。

### 2.2 业绩归属与佣金分账是两张图

| 图 | 回答的问题 | 决定 |
|---|---|---|
| 业绩归属（Credit） | 这单算谁的指标 | 达成率、系数档位 |
| 佣金分账（Pay） | 这笔佣金分给谁 | 个人应发金额 |

业务里"AS 成单按 1:1 分给 SS"只发生在第二张图上：SS 拿到钱，但**不因此增加达成率**。若把分账写进业绩归集，会出现连锁错误——SS 分到一半业绩后达成率跳档，SS 其余订单的系数也跟着变，最后连池资格都可能变。

因此：`Attainment.Actual` 的求和口径固定为「业绩归属规则」，`SplitLine` 不得回写 `Attainment`。这是个不变式（§10 I10）。

### 2.3 池是预算，不是费率

现有实现按 `BPS × 基数` 注资（费率模型）。业务真相是"产品线设置奖金池总额"（预算模型）：

| 维度 | 费率模型（现状） | 预算模型（目标） |
|---|---|---|
| 池总额 | 随订单额浮动 | 期初给定，固定 |
| 消耗 | 每单注资 | 按成单顺序领取，领完为止 |
| 超发 | 不可能 | 不会超发，但后面的单领不到 → 必须告警 |
| 结转 | 留存比例 | 剩余额结转下期 |

**关键取舍：池不够时不做按比例缩放。** 按比例缩放会让早单金额随后续订单变化，破坏"先到先得"，且每次补录订单都要重算全部历史单。正确做法是：按全序逐单领取，领到 0 的订单落 `Exhausted` 标记 + 告警，结算期由人决定是否追加预算。

预算金额属于**事实**（`Facts.Pools`，进 `factsDigest`），发放条件属于**规则**。若把预算写进规则，规则改版就会改预算，重算差额无法归因。

## 3. 事实快照增量

```go
type KPI string // "contract" | "revenue"

type OrderLine struct {
    ID       OrderLineID
    Product  string
    Contract money.Money // 合同额
    Discount money.Money
    Return   money.Money
    Revenue  money.Money // 实际收入额（财务确认口径）
    Cost     money.Money
}

func (l OrderLine) BaseOf(k KPI) money.Money {
    switch k {
    case KPIRevenue:
        return l.Revenue - l.Return
    default:
        return l.Contract - l.Discount - l.Return
    }
}

type Order struct {
    // ... 原有字段
    ClosedAt time.Time  // 成单时间：决定季度因子与池领取顺序
    Class    OrderClass // 订单分类：PS 分账公式的维度
}

type Target struct {
    Person   PersonID
    Period   Period
    Contract money.Money
    Revenue  money.Money
}

type RelationKind string // "ad_as" | "ss_as"

type Relation struct {
    From, To PersonID
    Kind     RelationKind
}

type PoolDef struct {
    ID     PoolID
    Line   ProductLineID
    Role   RoleID // 空 = 不限角色（产品线级池）
    Period Period
    Budget money.Money
}

type Facts struct {
    // ... 原有字段
    Targets   []Target
    Relations []Relation
    Pools     []PoolDef
}
```

三个字段都用**切片而非 map**：`Target` 与 `PoolDef` 自身带 `Period`，同一个人/池可以跨期存在多份记录，用 map 会覆盖掉——历史重算时拿不到原期目标额。切片顺序不影响摘要（`canonical` 会排序），因此不引入不确定性。

三条约束：

1. `ClosedAt` 必须是业务时间（成单日），不是录入时间。这是双时间轴的基本要求。
2. `Relations` 必须快照冻结。组织调整后重算历史，SS/AS 配对必须还是当时的——否则"去年这单为什么分给这个人"回答不了。
3. `Person.Role` 作为兜底角色；订单上的 `Participant.Role` 优先。同一人在不同订单可扮演不同角色，这是业务事实，不要强行归一。

## 4. 规则模型增量

### 4.1 新增维度（`Scope`）

| 维度 | 字段 | 特异性权重 | 用途 |
|---|---|---|---|
| 达成率档 | `Bands []BandID` | 8 | 「高业绩区间倍率 2.5×」 |
| 部门 | `Depts []DeptID` | 8 | 部门 A 独立规则 |
| 计佣口径 | `KPIs []KPI` | 8 | 合同口径与收入口径的基准费率不同 |
| 订单分类 | `OrderClasses []OrderClass` | 4 | PS 公式的「订单分类」 |

`MatchCtx` 同步增加 `Band / OrderClass / Dept / KPI` 四个字段。

**口径必须是 `Scope` 维度，不能放 `Action`。** M2 落地时把设计稿里的 `Action.KPIs` 挪成了 `Scope.KPIs`：合同佣金与收入佣金的费率通常不同，这是「选哪条规则」的问题，不是「这条规则怎么算」的问题。放进 `Action` 会让冲突检测看不见它，等于放任两条费率不同的规则同名互踢。

**人级例外一律走 `Overlay`，不开 `Scope.Persons`。** 一旦允许按人配规则，矩阵会从几十格炸到几千格，发布期体检（§13）就失去意义。同理 `MatchCtx` 也不加 `Person`——加了就一定有人去加 `Scope.Persons`。
### 4.2 新增阶段与动作

```go
const (
    PhaseAttain Phase = "attain" // 业绩归集：定达成率档
    PhaseFactor Phase = "factor" // 时间/产品因子
    PhaseSplit  Phase = "split"  // 关系分账
    // PhaseFund / PhaseDirect / PhaseDistribute / PhaseManager 沿用
)

const (
    ActCredit        ActionKind = "credit"         // 业绩归属
    ActTimeFactor    ActionKind = "time_factor"    // 季度因子
    ActProductFactor ActionKind = "product_factor" // 产品因子
    ActSplit         ActionKind = "split"          // SS/AS 分账
)
```

**冲突检测改为作用域交集判定，不再按目录枚举上下文。** 原设计打算在 `rules.contextsFor` 里按「产品线 × 角色 × 档位 × 订单分类」全量枚举 160 格，M2 落地时改成 `Scope.Overlaps` 两两比较——枚举有两个固有缺陷：新增维度忘补枚举就静默漏检（靠自觉），且没有商品的期间会把配置冲突判成「无冲突」（靠数据）。交集判定是 O(规则数²)，与目录无关，也不会漏维度。

### 4.3 系数档位

```go
// Band 是达成率区间。FromBPS 含、ToBPS 不含；ToBPS == 0 表示无上界。
type Band struct {
    ID       BandID
    FromBPS  int64 // 7000 = 70%
    ToBPS    int64 // 0 = +∞
    CoeffBPS int64 // 该档倍数：18000 = 基准的 1.8 倍（不是费率）
}
```

### 4.3.1 倍率模型（Q1 已定：倍率）

**档位只给倍数，基准费率单独一条规则，全链一次累乘、一次舍入。**

```
amount = base × BaseBPS × BandBPS × Π(FactorBPS) / 10000^(2+n)
```

三个 bps 来源的分工：

| 名字 | 含义 | 配置位置 | 典型值 |
|---|---|---|---|
| `BaseBPS` | 该 (产品线 × 角色) 的基准佣金率 | `PhaseDirect` 规则 | 100 bps = 1.0% |
| `BandBPS` | 达成率档位的**倍数** | 档位表 `Band.CoeffBPS` | 18000 = 1.8× |
| 因子 `BPS` | 时间 / 产品 / 区域的**倍数** | `PhaseFactor` 规则 | 12000 / 15000 / 11000 |

数值示例（基数 100 万）：

```
1,000,000 × 1.0%(基准) × 1.8(档位) × 1.2(时间) × 1.5(产品) = 32,400.00
```

选定倍率的理由（已定，不再比较）：

- **与原文同构**：原文把系数、区域、订单分类、时间因子、产品因子一律描述成相乘因子，全链一个 `ApplyChain`，不必为费率另开路径
- **天然单调**：档位只升不降，`CoeffBPS` 单调性由数值语义保证，不靠校验兜底
- **改基准半径小**：1.0% → 1.1% 只改一条规则，全档同步
- **代价明确**：改基准等于全公司重算，必须靠发布预览 + 金标回归 + `CalcRunID` 变更拦住

模型改动：

```go
type Action struct {
    // ... 原有字段
    BaseBPS       int64 // PhaseDirect 的基准费率
    MultiplierBPS int64 // PhaseFactor 的倍数，10000 = 1.0
}
```

**`Action.BPS` 语义收回**：现有实现的 `BPS` 是"最终费率"，倍率模型下它只能表示 `BaseBPS`。存量规则迁移时 `BPS` 一律迁成 `BaseBPS`，档位另配。这是语义变更，必须与 `EngineVersion` bump 同批发布——否则幂等键不变，线上数字不会动。

#### 区域是乘数（Q1b 已定）

区域**不参与选费率**，只提供乘数（华东 1.1、华南 0.95 这类）。

| 维度 | 允许出现的阶段 | 说明 |
|---|---|---|
| `Scope.Territories` | `PhaseFactor` | 用来选"哪条区域乘数规则命中" |
| `Scope.Territories` | `PhaseDirect` / `PhaseAttain` | **禁止**，编译期直接 error |

理由：若区域既是筛选维度（决定走哪套费率）又是乘数，同一维度会被乘两次，且从结果上看不出来——1.1 × 1.1 与"配成 1.21"完全无法区分。禁止比"靠约定"可靠。

编译期校验（并入 `Compile`，命中即 error）：

- `PhaseDirect` / `PhaseAttain` 的 `Scope.Territories` 非空
- 因子 `Kind` 出现在别的阶段（`time_factor` 写在 `PhaseDirect`），或 `PhaseFactor` 里混入非因子动作（`detectFactorRules`）
- 同一个 `Kind` 的两条因子，特异性与优先级都相同且作用域相交（`detectConflicts` 按 `Phase/Kind` 分域裁决，见 §4.4）

**判定用交叉相乘，不用除法**：

```go
// 命中判定：actual/target ∈ [From, To)
hit := actual*10000 >= band.FromBPS*target &&
    (band.ToBPS == 0 || actual*10000 < band.ToBPS*target)
```

原因：`actual*10000/target` 一旦先取整，69.996% 会被舍成 70.00% 而跳档，跨档边界正好是大额订单最集中的地方（差一档就是几千块）。`RateBPS` 只用于展示与 Trace，不参与裁决。

编译期校验（`detectBandGaps`，命中即 error）：

- **每条 `PhaseAttain` 规则自带完整档位表**：最低档 `FromBPS == 0`、最高档 `ToBPS == 0`，相邻档首尾相接（不重叠、无洞）
- `CoeffBPS` 单调不减且为正（高业绩档倍数不得低于低档）——业务上必然成立，违反必是配置错误
- 档位表只允许配在 `PhaseAttain`；配到 `PhaseDirect` 等其它阶段直接报错
- `PhaseAttain` 的作用域只允许 角色 / 部门 / 口径；出现产品线 / 系列 / 池 / 区域 / 档位 / 订单分类即报错（`detectAttainScope`）

要求"每条规则的表自带完整覆盖"，而不是"同一 (角色 × 口径) 跨规则拼接后再校验"：前者是局部可判定的，且天然挡住"特化规则只补了几档、剩下几档落空"这种最难发现的配置事故。跨规则拼接则必须先把所有规则的作用域求并，判定复杂度随规则数爆炸，还会在"特化规则与通用规则谁补谁"上引入第二套裁决逻辑。

**档位表的粒度是 (角色 × 口径)，不是人。** 达成率是每人每期一条，但倍数表挂在规则上：若按人配表，同一个人在不同订单上角色不同（成单人 / 管理者），档位就会随订单漂移，且与"角色决定费率"这条既有语义打架。个人差异靠 `Targets` 体现——目标不同，同一张表落到的档位自然不同。

### 4.4 因子

时间因子、产品因子、区域因子三者都是**乘数**（10000 = 1.0），统一走 `PhaseFactor`：

```go
type Action struct {
    // ... 原有字段
    BaseBPS       int64    // PhaseDirect 的基准费率，100 bps = 1.0%
    MultiplierBPS int64    // PhaseFactor 的倍数，10000 = 1.0，20000 = 2.0
    Bands         []Band   // 档位表，只允许配在 PhaseAttain（见 §4.3.1）
    ShareMode     ShareMode // pair1to1 | splitSubordinates | none
    DistMode      DistMode  // equal | all | weight | fifo
    AllocTo       RoleID    // DistMode=all 时的收款角色
}
```

**`Action.KPIs` 不存在，计佣口径是 `Scope.KPIs`。** 合同佣金与收入佣金的基准费率通常不同，这属于"选哪条规则"，不属于"这条规则怎么算"；放进 `Action` 会让冲突检测看不见它，等于放任两条费率不同的规则同名互踢。M2 落地时已按此调整。

同一 `Kind` 只取一条（按 `better` 裁决），不同 `Kind` 相乘。避免"两条时间因子同时生效"这种无意义配置。

三种 `Kind` 与作用域：

| Kind | 作用域维度 | 说明 |
|---|---|---|
| `time_factor` | 季度（由 `ClosedAt` 推导，作为 `Scope` 的季度维度） | Q1~Q4 各一条，`MultiplierBPS` ∈ [10000, 20000] |
| `product_factor` | 产品线 / 系列 | 系列优先于产品线（既有特异性裁决） |
| `territory_factor` | 区域 | 区域只能在这里出现，见 §4.3.1 |

落地时的四条判断（M3）：

1. **裁决域是 `Phase/Kind`，不是整个 `PhaseFactor`。** 时间、产品、区域本就该同时命中并相乘，若按整个阶段判冲突，任何一套完整因子配置都会被自己判成不可发布。实现上 `arbitrationKey` 给 `PhaseFactor` 拼上 `Kind`，其它阶段仍按 `Phase` 成域。
2. **缺配是少乘，不是清零。** 某季度没有时间因子 → 倍数 1.0；某产品线没有产品因子 → 1.0。反过来 `MultiplierBPS <= 0` 是编译期 error：0 会把整条链乘没，而从结果上只表现为"这个月佣金异常低"。真需要清零请用 `Overlay exempt`，那是显式动作。
3. **季度由 `Order.ClosedAt` 推导（`domain.QuarterOf`），不由付款时间决定。** 9 月底成单、10 月回款的订单属于 Q3。季度是 `Scope` 的一等维度（`Scope.Quarters`），不是把 "2026Q4" 塞进字符串维度——否则 `Overlaps` 看不见它，冲突检测也就瞎了。规则里只写季度不写年份，"每年 Q4 旺季 1.2 倍"是一条规则而不是四条。
4. **只写系列不写产品线的产品因子是 error。** 系列特异性 4、产品线级规则 8，前者会被静默压过；要么写明 `Lines + Series`（8+4=12），要么别配。

## 5. 流水线（八段）

在 ARCHITECTURE §3 的六段上插入两段（归集、因子），并把池阶段改成"预言算 + FIFO 领取"。顺序**由事实全序决定**，不由切片顺序决定。

| # | 段 | 输入 | 输出 | 关键断言 |
|---|---|---|---|---|
| 0 | 归集 `attain` | 全部订单行 + `Targets` | `[]Attainment` | 每个 (人, 口径) 恰好命中一档 |
| 1 | 基数 | 行项目 | 分口径基数 | 基数 ≤ 0 跳过；合同/收入各自独立 |
| 2 | 因子 | 行 + 季度 + 产品线/系列 + 区域 | `[]FactorHit` | 同 Kind 唯一；缺配按 1.0；不落金额 |
| 3 | 直接佣金 | 行 + 角色 + 档位 + 因子 | `DirectLine` | 单次舍入，Trace 可重放；每行每口径一条 |
| 4 | 分账 | `DirectLine` + 关系图 | `SplitLine` | `Σ split == 分账前金额`，不级联 |
| 5 | 池领取 | 行 + `PoolDef.Budget` | `PoolClaim` | 领取 ≤ 剩余；全序单调 |
| 6 | 池分发 | Claim + 参与者 | `Distribution` | `Budget == Distributed + CarryOver` |
| 7 | 管理奖金 | **分账前** `DirectLine.Amount` + 成单人链 | `ManagerBonus` | 基数不随分账变，池不参与（§7.1 / §8.4） |
| 8 | 结算 | — | `PersonTotal` | 三式守恒（§10） |

执行顺序固定为：阶段 0 全量 → 阶段 1~4 按 `(ClosedAt, OrderID, LineID)` → 阶段 5~6 同一全序 → 阶段 7~8。

**阶段 2 与 3 必须合并在一次 `ApplyChain` 里**：因子段只产出 `FactorHit`（命中哪条规则、倍数多少），不产出金额。若把"乘完档位"先落成金额再逐步乘因子，每一步都会舍入一次，链越长偏差越大（§6.1）。因此实现上"因子段"不是一个独立的金额阶段，而是阶段 3 的输入。

阶段 5 与 6 可以合并成一次 FIFO 遍历，但产物分层保留：`PoolClaim` 记录"这单从池里领了多少"，`Distribution` 记录"这笔钱分给了谁"。合并会让"池没发完是因为没订单还是规则没配"无法区分。

### 5.1 双口径同时算（Q2 已定）

合同口径与收入口径**各算一笔，互不合并**：同一条订单行在同一个人身上产出两条 `DirectLine`，靠 `KPI` 字段区分。

```go
type DirectLine struct {
    // ... 原有字段
    KPI      domain.KPI // contract | revenue
    Base     money.Money
    BandID   domain.BandID
    CoeffBPS int64 // 档位命中值
    Factors  []FactorHit
}
```

三个连带影响，都会改变 `Result` 的形状：

| 环节 | 双口径后的行为 |
|---|---|
| 归集（阶段 0） | 每人每期出**两条** `Attainment`（合同一条、收入一条），各自定档，两个档位可能不同 |
| 直接佣金（阶段 3） | 每行每人两条，金额分别计算，不做汇总后再算 |
| 分账（阶段 4） | 按 `(OrderID, LineID, KPI)` 分组守恒，两个口径各自分摊，余额各自给成单人 |
| 管理奖金（阶段 7） | 按**分账前** `DirectLine.Amount` 逐条上溯（§7.1），合同/收入两条分别进 `ManagerBonus`，靠 `KPI` 留痕 |
| 池领取（阶段 5） | **只取收入口径**（见下） |

### 5.2 池领取口径（默认）

池是奖励实际业绩的预算，因此 `ClaimBPS` 作用在**收入口径基数**上，与"合同佣金 + 收入佣金"两条个人佣金并存不冲突。若业务要求合同口径也入池，代价是同一产品线的池被两条口径各领一次，总量翻倍——需要的话请显式指定，不要默认。

### 5.3 本期人员分成额（Q2 后半）

"本期人员分的奖金额"在模型里就是 `Distribution` 按人聚合，产物必须能直接回答"某人本期从池里拿了多少、来自哪些单"：

```go
type PersonPoolShare struct {
    Person     PersonID
    Pool       PoolID
    Role       RoleID
    FromOrders []OrderID // 来源订单，按全序
    Amount     money.Money
}

type PersonTotal struct {
    // ... 原有字段
    DirectContract money.Money // 合同口径佣金
    DirectRevenue  money.Money // 收入口径佣金
    Pool           money.Money // 池分成合计
    Manager        money.Money
    Total          money.Money
}
```

口径锁定：池分成的参与人范围 = **本期产生 `PoolClaim` 的订单的参与人**。上期结转额在下期随新订单重新进入分配，不追认上期人员——否则"去年离职的人还在领今年的池"会无法解释，且每期都要回溯历史关系图。

## 6. 精度与舍入

| 对象 | 表示 | 舍入规则 |
|---|---|---|
| 金额 | `money.Money`（int64 分） | 禁止 float64 |
| 费率 / 倍率 | `int64` bps（10000 = 100%） | — |
| 达成率 | 不落成数，比较用交叉相乘 | 落盘仅 `RateBPS = floor` 供展示 |
| 因子链 | 分子分母 `big.Int` 累乘 | **最后一次**四舍五入 |
| 分账 / 池分发 | `money.Allocate` 最大余数法 | `Σ == total` 恒成立 |

### 6.1 因子链必须只舍一次

```
应得 = 基数 × 基准费率 × 档位倍数 × 时间 × 产品 × 区域
     = base × (b/10000) × (c/10000) × (t/10000) × (p/10000) × (r/10000)
```

若每步都 `ApplyRate`，四次舍入在 800 万级订单上会漂几分到几毛；若先把四个 bps 相乘，`int64` 会溢出（1e8 分 × 1e4⁴ = 1e24）。做法：

```go
// ApplyChain 对 base 依次施加乘数，只在最后舍入一次（远离零）。
// 中间用 big.Int 分子/分母累乘，order 量级小，成本可忽略。
func ApplyChain(base Money, bps ...int64) Money
```

单因子场景继续走 `ApplyRate` 快路径，两者结果必须一致（测试守住）。

**留痕必须可复算**：`Trace` 存的是 `Base / RateBPS / CoeffBPS / Factors / Weight / OverlayDelta` 原值，`Trace.Replay()` 用同一串 bps 重跑 `ApplyChain` 再叠加权重与覆盖层，结果必须逐分等于 `Amount`。不是"能看懂"，是"能算出同一个数"——`TestTraceReplaysAmount` 对全量 Trace 断言，demo 每次运行也自检。

### 6.2 舍入层级（沿用 §5.3）

- 行级：`ApplyChain` 一次
- 分账级：最大余数法，尾差在分账组内消化
- 池级：领取额受剩余额约束，不重算比例
- 汇总级：只做加法

## 7. 分账（SS / AS）

```go
type ShareMode string
const (
    SharePair1to1    ShareMode = "pair1to1"          // AS 成单：与配对 SS 各 50%
    ShareSplitSubs   ShareMode = "splitSubordinates" // SS 成单：与名下 AS 均分
)
```

规则：

| 成单人 | 分账对象 | 份额 |
|---|---|---|
| AS | 该 AS 的配对 SS（`ss_as` 关系） | AS 50% / SS 50% |
| SS | 名下全部 AS（一对多） | SS 与每个 AS 各 `1/(1+N)` |
| 其他 / 无配对 | 无 | 100% 自留 |

三条硬约束：

1. **不级联。** 一次分账后不再继续转分（SS 转出去的份额不再转给 SS 的上级）。级联会让一条订单行产生 N 层转移，且容易成环。实现上断言：`SplitLine.To` 不再作为 `From` 出现在同一 `(OrderID, LineID)` 的分账里。
2. **守恒。** `Σ SplitLine.Amount + 自留 == 分账前金额`，用 `Allocate` 拆，尾差给成单人。分账是零和转移，绝不产生新钱。
3. **关系图必须在快照里。** 配对缺失（AS 没有 SS）视为配置缺口：按 100% 自留并告警，不静默按 0 处理。

多 AS 时份额 `1/(1+N)` 用权重 `[1,1,...,1]` 直接 `Allocate`，不要先算整数百分比再乘——那样会丢分。

落地时补齐的四条（M4）：

1. **分账方式挂在 `PhaseDirect` 规则的 `Action.ShareMode` 上**，不是全局开关，也不单独成阶段规则。同一条订单行上，渠道角色的规则配 `pair1to1`、负责人规则保持全额自留，是完全合法的组合——"谁和谁分"本来就是按角色配的。
2. **关系只认方向。** 关系快照记 `From`=上级、`To`=下属（`ss_as` 即 SS→AS）。AS 成单要找它的 SS（`SuperiorsOf`），SS 成单要找名下 AS（`SubordinatesOf`）。若用对称的"对方"语义，SS 成单时会把上级当搭档，一个 AS 会被拆两次。
3. **尾差给成单人靠排序实现，不靠分支。** 权重切片固定把成单人放在第 0 位，`Allocate` 的最大余数法按索引升序补尾差，于是 1.00 元三人拆得到 `[34,33,33]`。收款人按 ID 升序，保证换关系录入顺序结果不变（I9）。
4. **分账不进 `Trace`。** 它不是倍率链的一环，`Replay()` 那套 `Base × Πbps` 对它无意义；它自己的留痕就是 `SplitLine` 这一条 `From → To → Amount`，复算方式是"Σ 分出 + 自留 == 分账前金额"。硬塞进 Trace 只会让 I8 变成假命题。

### 7.1 分账与管理奖的关系（Q7 已定：方案 A 分账前）

**管理奖金基数 = 分账前 `DirectLine.Amount` 全额，沿"成单人"的组织链上溯。分账只改收入分配，不改管理奖的归属链。**

```
AS 成单 14,580 ──► 分账 AS 7,290 + SS 7,290     （阶段 4，零和转移）
              └──► 管理奖基数 = 14,580           （阶段 7，走 AS 的上级链，不看分账结果）
```

| | 方案 A（已选） | 方案 B（未选） |
|---|---|---|
| 基数 | `DirectLine.Amount`（分账前） | `SplitLine.Amount`（分账后净额） |
| 组织链 | 成单人一条链 | 每个收款人各自一条链 |
| SS 的上级 | 拿不到这笔管理奖 | 按其份额上溯 |
| 链断 | 只影响成单人链，可断言 | 每个收款人链都可能断，静默少发 |

选 A 的三条理由：

1. **管理奖的正当性来自辅导了成单人，不来自钱最后落在谁账上。** 分账是收入再分配，不改变"这单是谁促成的"。
2. **链断不吞钱。** A 的总额只取决于成单人链是否完整，可以写死守恒断言；B 依赖每个收款人的链，缺一环就静默少发——正是架构文档反复警告的资损形态。
3. **不需要多链去重。** B 下同一人可能在不同收款人的链上以不同层级出现，需额外定义合并规则；A 只有一条链，无歧义。

**要接受的代价**：SS 分到 7,290，但 SS 的上级一分没有。若业务认为"SS 的上级也辅导了这笔"，应改选 B 并同时定义链断兜底（建议按 1 层截断并告警，不要静默归零）。

配套断言（并入 §10）：

- `ManagerBonus.Base == 对应 DirectLine.Amount`（分账前全额），不得等于任何 `SplitLine.Amount`
- `Σ ManagerBonus` 与 `Splits` 完全无关：改动分账规则不改变管理奖总额

## 8. 奖金池

### 8.1 领取（阶段 5）

```go
type PoolClaim struct {
    OrderID, LineID string
    Pool            PoolID
    Budget          money.Money // 期初
    Remaining       money.Money // 领取前剩余
    Claimed         money.Money // 本单领取
    Exhausted       bool        // 领取后耗尽
    RuleID          RuleID
}
```

领取额 = `min(行基数 × ClaimBPS, 剩余额)`。若业务语义是"每单固定额"（而非按基数比例），把 `ClaimBPS` 换成 `FixedAmount` 即可，接口不变——**这是唯一需要业务确认的池语义分叉点**（§11 Q5）。

实现上 `ClaimBPS` 就是 `Action.BaseBPS`：领取和直接佣金是同一件事——"基数 × 费率"，没理由为它另开一个字段名，否则读规则的人要记两套。

三条实现约定：

1. **全序是 `(ClosedAt, OrderID, LineID)`**，与阶段 0~4 共用同一个序（§5 末）。不排序等于让事实切片的录入顺序决定谁拿到钱（I9）。
2. **领到 0 的单仍要留一条 `PoolClaim`**，`Exhausted=true`。省掉这条记录就等于让"后面几单池没有钱"变成查无此事的现象，而这恰恰是最需要看见的事。
3. **封顶不进倍率链**。`Trace` 用 `Base × RateBPS` 算出"应领 `want`"，预算截断的部分走 `OverlayDelta = claimed − want`，这样 `Trace.Replay()` 仍逐分复算得出 `Claimed`（I8），留痕不会因为封顶而失真。`ApplyChain` 只乘不截断，别为池子单开一条链。

### 8.2 分发（阶段 6）

| `DistMode` | 语义 | 对应业务 |
|---|---|---|
| `equal` | 本单领取额在参与人之间均分 | "奖金池分账：均分" |
| `all` | 全给指定角色（`AllocTo`） | "奖金池分账：所有" |
| `weight` | 按角色权重表（`WeightTable`）× 参与份额 | 部门 A 按角色设规则 |

**"按成单顺序分"不是 `DistMode`**。它不是"这一单的钱给谁"，而是"谁的订单先领到钱"——那是阶段 5 的全序。砍掉这个枚举值，是因为它和另外三个不是同一个问题：前者决定**何时领**，后者决定**领到的怎么分**；塞进一个枚举就会出现"选了 fifo 是不是就不用均分了"这种无法回答的问题。

三条实现约定：

1. **均分用最大余数法**（`money.Allocate` + 权重全 1），不先算 `1/N` 的整数百分比再乘——那会把尾差丢在舍入里。尾差按人 ID 升序给，结果与录入顺序无关。
2. **权重表里没有的角色不参与**，不做"按 1 兜底"。兜底会把配置遗漏变成一笔金额正确、对象错误的静默错发。
3. **分不出去的钱退回留存**（→ `CarryOver`）并告警：规则没配全时宁可让钱留在池里可见，也不要让它凭空消失或默认发给负责人。

### 8.3 分池粒度

`PoolDef{Line, Role, Period, Budget}`。`Role` 为空 = 产品线级池；非空 = 部门 A 那种"按产品线和角色"的池。同一产品线可并存多个池（负责人池 + 角色池），互不影响。

「互不影响」在实现上是三件事，缺一件就会真的互相影响：

1. **裁决域按目标池切分**。`rules.arbitrationKey` 对 `PhaseFund` 返回 `fund/<池ID>`，不是整个 `PhaseFund` 一个域。否则"产品线池 4% + 负责人池 2%"会被判成冲突（两条规则同阶段、作用域重叠），而它们本来就应该同时生效。
2. **一行喂多个池**，所以取规则用 `Index.All`（逐域取最优再合并）而非 `Best`。指向同一个池的多条规则之间才互相裁决。
3. **领取按行去重**。查找上下文里的 `Role` 逐个取成单参与角色（排序后遍历，保证 I9），同一行对同一个池最多领一次——否则总量会随参与人数翻倍，且是静默翻倍。

### 8.4 池分成与管理奖的关系（Q7 方案 A 的直接推论）

**池分成不参与管理奖上溯。管理奖的唯一基数是 `DirectLine.Amount`。**

理由与 §7.1 同源，且更彻底：池本身是"产品线给成单负责人的额外奖励"（业务真相原文），它已经是对成单行为的二次奖励；再让池金额沿组织链衰减一次，等于同一笔钱被奖励两次管理者，且池的预算守恒（I2）会被管理奖打破——池发出的 100% 加上衰减出的 10% 就超过预算了。

| 收入类型 | 是否上溯管理奖 | 说明 |
|---|---|---|
| 直接佣金（合同口径 / 收入口径） | **是**，基数为分账前 `DirectLine.Amount` | §7.1 |
| 池分成 `Distribution` | **否** | 本节 |
| 管理奖 `ManagerBonus` | 不再上溯 | 避免无限递归 |

配套断言（并入 §10）：

- `Σ ManagerBonus` 之和与 `Distributions` 完全无关：改动池规则不改变管理奖总额
- 每条 `ManagerBonus.Base` 必须能在 `Directs` 里找到同 `(OrderID, LineID, Person, KPI)` 且金额相等的记录

**若将来业务要求池也上溯**，必须同时做两件事，缺一不可：① 池预算按"发放额 + 管理奖衰减额"整体封顶，否则 I2 的 `Budget == Distributed + CarryOver` 直接不成立；② `PoolSettlement` 增加 `ManagerLeak` 字段单独留痕。这是一次结构性变更，不要顺手改。

## 9. 计算模式

业务要求"全量 / 按人 / 按订单"三种。**只有一个算钱入口，另外两种是投影**：

```go
func Run(facts, rs, opts) (Result, error)                          // 唯一入口，全量
func (r Result) ProjectByPerson(ids ...PersonID) Result            // 裁剪输出
func (r Result) ProjectByOrder(ids ...OrderID) Result              // 裁剪输出
```

为什么不能有独立引擎：

- 达成率是**期间函数**，只喂一个人的订单算出来的达成率是错的，系数跟着错；
- 池是**全局序列函数**，只算某单无法知道它前面被领走多少；
- 订单量少、单笔金额大（ARCHITECTURE §1 第三条），全量重算成本可忽略。

投影的唯一职责是裁输出，不得触发重算。若将来真要提速，优化点在全量内核的缓存，而不是做局部引擎。

两条投影的边界不一样，必须分开说，否则很容易用法上串：

| | `ProjectByPerson` | `ProjectByOrder` |
|---|---|---|
| `Persons` | **原样保留**这个人的结算行（它本来就是这个人的期间合计） | **重新求和**：把裁剪后的明细喂回 `aggregate.go`，得到「这一单发了多少、给了谁」 |
| 明细筛选 | 直接佣金 / 池分发 / Trace / 达成率按人筛；分账**两方都留**（只留一侧净额就不对了） | 一律按 `OrderID` 筛 |
| 领取 | 按保留下来的「订单行」反查（人只通过参与过的行与领取相关） | 按 `OrderID` 筛 |
| 不裁的部分 | `Pools` / `Warnings`（整期预算对账，不能按人切） | `Attainments` / `Pools` / `Warnings`（达成率与预算都不是单笔订单的属性） |
| `CalcRunID` | 不变 | 不变 |

`ProjectByOrder` 要重算 `Persons` 不是"破了不重算的规矩"：金额一分未动、没有查任何规则、`CalcRunID` 不变，只是把求和跑在子集上。反过来把一个月的 10 万塞进某一单的视图才是真的错。

求和只有一份实现（`internal/calc/aggregate.go` 的 `aggregatePersonTotals`），`Run` 与投影共用。分账净额必须同时记 `From` 负、`To` 正，投影若自己再写一遍求和，极易只记转入不记转出——那时 `Σ Split != 0` 就没处报了。

## 10. 不变式

前五条沿用 ARCHITECTURE §8，新增五条同样实现为**断言（返回 error），不是注释**：

| # | 不变式 | 违反含义 |
|---|---|---|
| I1 | 金额一律 `money.Money` | 精度污染 |
| I2 | 每池 `Budget == Distributed + CarryOver`，其中 `CarryOver := Budget − Distributed` | 池子丢钱或超发 |
| I3 | `Σ PersonTotal.Total == Σ DirectLine.Amount(分账前) + Σ Distributed + Σ ManagerBonus`，因为 `Σ PersonTotal.Split == 0` | 汇总与明细不一致 |
| I11 | 每条 `(OrderID, LineID, Person, KPI)` 至多一条 `DirectLine`，两口径不得合并成一条 | 口径串味 |
| I12 | `ManagerBonus.Base` 必须等于对应分账前 `DirectLine.Amount`，且 `Σ ManagerBonus` 与 `Splits`、`Distributions` 均无关 | 管理奖基数串到分账后或池 |
| I4 | `CalcRunID` 四要素任一变化必须变 ID | 幂等吞掉重算 |
| I5 | `Recalculate` 先断言 `Σdelta == Σnew − Σold`；仅准入 `Locked` 期间；每条分录带由四要素推导的 `Cause`，差额非零而 `Cause` 为空即拒绝 | 差额入账不平 / 重算无从归因 / 不可复现的差异被固化 |
| I6 | `Σ SplitLine.Amount + 自留 == 分账前金额`；`Σ PersonTotal.Split == 0`；每条分账的 `From` 必须是某条 `DirectLine` 受益人；不级联 | 分账凭空造钱/重复转移 |
| I7 | 每个 (人, 口径) 达成率恰好命中一档；档位覆盖无洞、无重叠 | 系数取不到或取两条 |
| I8 | `Amount == round(Base × Πbps)`，且能从 Trace 重放复算 | 结果不可解释 |
| I9 | 结果与 `Orders` / `Lines` 切片顺序无关 | 结果依赖录入顺序 |
| I10 | `Σ Attainment.Actual` 不受分账影响 | 业绩与佣金串味 |

I2 的 `CarryOver` 是**差出来的**，不是记出来的：写成 `Budget − Distributed` 后式子恒成立，无需再校验两个独立累加器是否对得上。`PoolSettlement.Retained`（领到了但分不出去、退回留存的部分）是 `CarryOver` 的**子集**，两者不是并列的两份钱——把 `Retained` 也算进 `CarryOver` 会重复计一次，导致 `CarryOver` 虚高而 `Budget` 对不上。断言仍需保留：它守的是 `Distributed ≤ Budget`（不超发），而等式的另一半由构造方式保证。

I9 需要先修一个**现存缺陷**：`calc.Digest` 直接 `json.Marshal(facts)`，`Orders` 切片顺序不同会得到不同 `factsDigest`，进而不同 `CalcRunID`——同事实、同规则、同代码，录入顺序一换就变成"需要重算"，幂等失效。修法：摘要前对 `Orders`（按 ID）、`Lines`（按 ID）、`Relations`（按三元组）排序，或改走规范化编码。`TestCalcRunIDIgnoresMapOrder` 只覆盖了 map，需补 `TestDigestIgnoresSliceOrder`。

## 13. 发布期体检新增项

沿用"冲突拒发、缺口告警"的分级（ARCHITECTURE §4.4）：

| 检查 | 级别 | 理由 |
|---|---|---|
| 档位覆盖有洞 / 重叠 / 倍数非单调 / 未覆盖 `[0,+∞)` | **error** | 倍数取不到 = 少发钱且不报错 |
| `PhaseAttain` 规则未配档位表，或档位表配在其它阶段 | **error** | 两者都是配错了地方，运行时无法兜底 |
| `PhaseAttain` 的 `Scope` 出现产品线 / 系列 / 池 / 区域 / 档位 / 订单分类 | **error** | 达成率是 (人, 口径) 的函数，按这些维度切会使同一个人不同订单取到不同档位 |
| `PhaseDirect` / `PhaseAttain` 的 `Scope.Territories` 非空 | **error** | 区域是乘数，配在这里会被乘两次 |
| 因子 `MultiplierBPS <= 0` | **error** | 0 会把整条链乘没，结果只表现为"佣金异常低" |
| 因子 `Kind` 配在非 `PhaseFactor` 阶段，或 `PhaseFactor` 混入非因子动作 | **error** | 运行时既不生效也不报错 |
| `product_factor` 只写系列不写产品线 | **error** | 系列特异性 4 会被产品线级 8 静默压过 |
| 每个 (产品线 × 角色 × 口径) 有基准费率 `BaseBPS` | gap 告警 | 基准缺失 = 整类订单算 0 |
| 关系图：AS 无配对 SS、SS 无下属、关系成环 | 运行时**告警** + 100% 自留 | 关系是事实不是规则，发布期无从判定；按 0 处理才是资损 |
| `Action.ShareMode` 配在非 `PhaseDirect` 阶段 | **error** | 分账只作用于直接佣金，配在池/管理奖上永远不会被读到 |
| `Action.ShareMode` 取未定义值 | **error** | 会一路传到运行时，最后静默按 100% 自留 |
| 每个 (产品线 × 角色 × 档 × 订单分类) 有佣金规则 | gap 告警 | 矩阵扩到 3~4 维后洞更多 |
| 每季度有且仅有一条时间因子 | gap 告警 | 漏配 = 整季少算 20% |
| 每条产品线有产品因子 | gap 告警 | 同上 |
| `PhaseDistribute` 规则未配 `DistMode` | **error** | 领到的钱无处可去，会全额退回结转且只在结算层可见 |
| `DistMode` 取未定义值 | **error** | `runPools` 走 `default` 会全额留存——看似安全，实为领了没发的静默错配 |
| `DistMode` 配在非 `PhaseDistribute` 阶段 | **error** | 池两层是领取与分发，配在 `PhaseFund` 上没人读 |
| `DistAll` 未指定 `AllocTo` / `DistWeight` 未给 `WeightTable` | **error** | 分发时无对象可选，只能全额留存 |
| `RetainBPS` 越界（`<0` 或 `>10000`） | **error** | 负数凭空造钱，超过 100% 发出的比领到的还多 |
| 有 `PhaseFund` 规则指向某池，但该池无分发规则 | gap 告警 | 领了必然全留；与"池有预算无规则"是两件事，前者是规则配漏，后者是事实配漏 |
| 池预算 > 0 但池无分发规则 | gap 告警 | 有预算没规则 = 全额结转 |

矩阵视图扩成「产品线 × 角色 × 档位」三维，仍可全量枚举（160 格内），保持"发布期全集 == 运行时命中全集"的口径一致性。

上表中档位三类 error、attain 作用域、区域禁入与三行因子校验已分别自 M2 / M3 起在 `Compile` 内生效；两条因子 gap（每季度时间因子、每条产品线产品因子）自 M3 起输出。池的六项 error（`detectPoolRules`）与"领了没规则分发"的 gap 自 M5 起生效。

注意：**枚举只用于缺口告警，不用于冲突检测**。冲突必须按 `Scope.Overlaps` 两两判定（§4.2 末）——枚举既会漏掉目录里没有的产品组合，又会把"两条规则作用域本不相交"误判成冲突。

## 14. 数值示例（可作金标用例）

**O-2001**：AS 成单，合同 500,000.00、收入 450,000.00；合同目标 600,000.00、收入目标 500,000.00；Q3；产品 A1；池剩余 60,000.00。

| 步骤 | 计算 | 结果 |
|---|---|---|
| 达成率（收入口径） | 450,000 / 500,000 = 90.00% | 命中 [70%,100%) 档 → 倍数 1.8× |
| 基准费率 | `R-BASE-AS`（产品线 A × AS） | 1.0% → 100 bps |
| 档位倍率 | `R-BAND-AS-NORMAL` | 1.8× → 18000 bps |
| 时间因子 | `R-TIME-Q3` | 1.2× → 12000 bps |
| 产品因子 | `R-PROD-A1` | 1.5× → 15000 bps |
| 区域因子 | 华东无加成（默认 1.0） | 10000 bps |
| 分账前佣金 | `ApplyChain(450000, 100, 18000, 12000, 15000, 10000)` | **14,580.00** |
| 分账 AS→SS 1:1 | 14,580 × [1,1] | AS 7,290.00 / SS 7,290.00 |
| 池领取 | 450,000 × 0.5% = 2,250，剩余足额 | 2,250.00 |
| 池分发（均分） | 2,250 × [1,1] | AS 1,125.00 / SS 1,125.00 |
| 管理奖金 | **分账前** 14,580 × 10%（AS 的上级 AD，§7.1 方案 A） | 1,458.00 |
| **合计** | AS 8,415.00 / SS 8,415.00 / AD 1,458.00 | 18,288.00 |

守恒核对：`8,415 + 8,415 + 1,458 = 18,288 = 14,580（佣金）+ 2,250（池）+ 1,458（管理）` ✓

两条用例专门守边界：

- **I10 业绩与佣金分离**：SS 拿到 7,290，但达成率不变（业绩记在 AS 名下）
- **I12 管理奖基数是分账前**：AD 拿 10% × **14,580**，不是 10% × 7,290（= 729）。若某次改动后 AD 变成 729，说明管理奖基数被串到了 `SplitLine` 上。同时注意 SS 那侧的上级在本例中拿不到任何管理奖——这是方案 A 的既定行为（§7.1），不是缺陷

池分成的 2,250 不再上溯管理奖（§8.4）：若也上溯，AD 会多拿 225，池的 `Budget == Distributed + CarryOver` 立刻不成立。

Trace 形态（阶段 3）：

> 14,580.00 = 450,000.00 × 1.0%（R-BASE-AS）× 1.8（R-BAND-AS-NORMAL，达成率 90.00%，档 [70%,100%)）× 1.2（R-TIME-Q3）× 1.5（R-PROD-A1）× 1.0（区域华东，无加成）

倍率化的关键收益就在这一行：改基准 1.0% → 1.1% 只动 `R-BASE-AS` 一条，档位与因子全不变；若为费率模型，1.8%/2.16%/3.0% 三个档都得改。

M1 实际落地的三处判断，供后续核对：

1. `Targets` / `Pools` 用切片而非 map（见 §3 说明），`canonical` 负责排序，摘要仍稳定。
2. `Directs` 在 `Run` 内按 `(OrderID, LineID, Person, Role)` 排序后再进入管理奖金与结算，所以"同事实不同录入顺序"得到的是**逐条相同**的结果，而不只是相同的 `CalcRunID`。`Trace` 保留生成顺序（承载叙事），不参与比对。
3. `Digest` 与 `runID` 移到 `internal/calc/digest.go`，`run.go` 只剩流水线。

M2 实际落地的三处判断，供后续核对：

1. **档位表挂在 `PhaseAttain` 规则上，按 (角色 × 口径) 配**，不按人配。达成率是每人每期一条，但倍数表若按人配，同一个人在不同订单上角色不同（成单人 / 管理者）就会取到不同档位，与"角色决定费率"的既有语义打架。个人差异靠 `Targets` 体现。
2. **无档位 = 倍率恒 1.0**，而不是"报错"或"取 0"。`RulesV1` 刻意不配档位，作为"结果与 v1 逐分钱一致"的回归基线；`Compile` 只对**配了 `PhaseAttain` 规则却给空表**的情况报错。
3. **`Attainment.Actual` 按参与者全额计入，不乘 `Participant.Weight`**。`Weight` 是分钱比例（Pay 图），`Actual` 是业绩归属（Credit 图），两者混用会让"分账比例调了 10%，达成率跟着掉"——即 I10 的直接违反。见 §11 Q10。

M4 实际落地的一条判断：**`PersonTotal.Direct` 保持分账前全额，分账净额单列 `Split`**。
若把分账折进 `Direct`（谁收钱谁记直接佣金），`Direct` 就同时承担"业绩归属"和"收款归属"两个含义：管理奖基数要读前者、对账要读后者，一处折进去另一处就必然串味（I12）。单列之后 `Σ Split == 0` 本身就是零和转移的可断言形式，I3 也就退化成"直接 + 池 + 管理"这个原来的式子。

M5 实际落地的五条判断，供后续核对：

1. **领取口径取收入**（§5.2 的默认值）。这条会改变 demo 的池金额（POOL-A 从合同口径 49,400 变成收入口径 44,400），所以它必须在 M5 一次改到位——池的"领多少"和直接佣金的"算多少"用不同口径是业务要求，不是实现差异。
2. **`fifo` 不是 `DistMode`**。设计稿初版把它列进枚举，实现时删掉：它回答的是"谁先领"（阶段 5 全序），不是"领到的怎么分"（阶段 6）。放同一枚举会出现"选了 fifo 还均不均分"这种无法回答的问题。
3. **封顶走 `OverlayDelta` 而非倍率链**。`Trace` 记录"应领 `want`"与"实领 `claimed`"，差额落 `OverlayDelta`，`Replay()` 仍逐分复算回 `Claimed`（I8）。若把封顶塞进 `ApplyChain`，要么改坏链的语义（只乘不截断），要么让重放对不上。
4. **`CarryOver := Budget − Distributed`**，`Retained` 只是它的子集（见 §10）。反过来"两个累加器都记 + 校验相加"会多一个可能不成立的等式。
5. **裁决域按目标池切**（`arbitrationKey` 返回 `fund/<池ID>`）。这是让"产品线池 + 负责人池"能共存的唯一办法；按阶段成域时，第二条规则会被判冲突，或静默把第一个池的领取清零——后者已在 `TestPoolMultiplePoolsPerLine` 里被钉住。

M6 实际落地的三条判断：

1. **`ManagerBonus` 补 `OrderID/LineID`**。只留 `Source + KPI + Base` 时，「金额能对上」不等于「对得上哪一条」——同一个人同口径的多条直接佣金金额可能相同，I12 的明细层断言就没法写成唯一的形式。补上两个字段后，`Base` 与 `DirectLine.Amount` 是一一对应的。
2. **求和抽成 `aggregatePersonTotals`，`Run` 与投影共用**。不是为了少写几行，而是为了让「分账净额 `From` 记负、`To` 记正」只有一处实现；投影若自己求和，漏记转出时 `Σ Split != 0` 不会有人发现。
3. **两条投影的 `Persons` 语义不同**（见 §9 表）：按人保留原行，按订单重新求和。判据是「这份人对小计对谁有意义」——期间合计对人有意义，对单笔订单没有。

M7 实际落地的三条判断：

1. **`Cause` 由 `CalcRunID` 四要素推导，不接受调用方自报**。自报的理由只会和实际入账的数字对不上，而台账的价值恰恰在于「事后不问人也能复核」。判据与 `CalcRunID` 完全一致，所以「`Cause` 非空」与「`CalcRunID` 变化」永远同时成立；反过来 `Cause` 为空而差额非零，说明结果变了却没有任何输入变化——那是引擎不确定，`Recalculate` 直接返回 error，不把一次不可复现的差异固化进台账。更细的归因（改了哪条规则、哪个池预算）不写进分录，拿 `Cause` 里的 `ruleSetVersion` / `factsDigest` 回快照上查即可。
2. **`Recalculate` 只对 `Locked` 期间开放**。未结算时直接 `Post` 就是重算，未锁定时 `Post` 覆盖草稿（ARCHITECTURE §7.2 的状态机）。若在这里放行，账面会从「只有一批 adjustment、没有 settlement」开始，`PeriodTotal` 等于差额而不是新合计，此后无论怎么调都补不回来——所以宁可前置拒绝，并提示正确的入口。
3. **`Post` 对 `Calculated` 期间是覆盖而非追加**，且分录按人 ID 排序生成。直接追加会让同一期间出现两套 settlement（账面凭空翻倍，两套各指不同 `CalcRunID`，事后无从判断哪套是终稿）；按 map 遍历顺序入账会让同一份重算两次写出两套编号不同的分录。两者都是静默错误，测试各钉一条。

M8 实际落地的四条判断：

1. **输入用代码写，期望用文本表写**。输入要复用 `demo` 的构造器并显式写出「相对基线只改了哪一处」（差异可读），所以只能是代码；期望要在 `git diff` 里一眼看出「P3 的池分成少了 1200 元」，所以不能用 JSON——几百行花括号里找一个小数点，评审时没人会真的看。代价是得自己写几十行解析，但这几十行换来的是「金标变更能被审」这个唯一目的。
2. **期望里冻结四要素身份，让两种失败分开**。`engine` / `ruleset` / `facts_digest` / `run_id` 一起进金标文件：输入变了报「输入快照或版本变了，不是算法变了」，输入没变而数字变了才是回归。混在一起时最危险——为了消红而 `-update`，会把一次真实的算法回退永久固化成正确结果。`run_id` 单独再分一档：三个分量全同而 `run_id` 变，说明幂等键的构成被改坏了（线上缓存集体失效），要查 `digest.go` 而不是改金标。
3. **按三层冻结，不只冻合计**。「合计对但归属错」是守恒断言看不见的：分账后按净额上溯管理奖，合计分毫不差、`Σ Split` 也是 0，只有上级的 `manager` 列变了。所以结算表按列拆（direct / contract / revenue / split / pool / manager / total），另加池对账与单笔投影——后者抓「钱在订单之间挪了」，那只在 `ProjectByOrder` 的合计上显形。
4. **语料自己也要被校验**。每个用例声明 `Tags`（它压什么语义），测试断言这些语义在结果里**真的出现**。没有这条，一次「顺手删掉分账规则」的改动会让 `split` 用例悄悄退化成 `baseline` 的复制品，而金标集仍然全绿地替它作证——那是最坏的绿灯。另有一条覆盖度检查，保证十条语义没有被任何用例压到时不至于无人察觉。

M2/M3 合起来才构成"倍率模型的完整语义"：M2 只让倍数参与，因子恒 1.0；M3 才把时间/产品/区域乘进来。**中间态（只上 M2）的结果小于最终结果**，所以两者必须同批上线；M3 的四条实现判断见 §4.4 末。
